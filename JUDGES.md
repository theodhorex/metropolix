# Judges Verification Guide: Claims to Evidence

This document maps each claim in the README to a command or link a judge can run, with the output we actually got when we ran it ourselves on **15 Nov 2026, 04:29 to 04:35 WIB**. Numbers that depend on the live chain (cities, battles, balances) change as people play; the commands do not.

Offline commands need Node 22+, `pnpm` and Rust (with the `wasm32-unknown-unknown` target for the wasm build). Commands marked `(needs network)` read the public NEAR testnet RPC; they need no account, wallet or key.

All `curl` examples use this shorthand. Paste it once:

```bash
RPC=https://test.rpc.fastnear.com
view() { curl -s $RPC -H 'content-type: application/json' -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"query\",\"params\":{\"request_type\":\"call_function\",\"finality\":\"final\",\"account_id\":\"metropolix.testnet\",\"method_name\":\"$1\",\"args_base64\":\"e30=\"}}" | python3 -c "import sys,json;print(bytes(json.load(sys.stdin)['result']['result']).decode())"; }
```

(`e30=` is the base64 of `{}`, so `view get_coin` calls the view with no arguments.)

## What is not proven

1. **The minute-to-minute city is simulated in your browser.** The simulation is deterministic (same seed and moves give the same city), but only its saved snapshot reaches the chain, and the chain bounds the snapshot instead of replaying every minute. A client can still choose how to play inside those bounds. `/verify` shows the rule-by-rule split of what the chain rejects, clamps or computes.
2. **The vault is a browser feature.** Treasure finds are rolled in the browser and are rate-limited only when you mint them (3 an hour, level-gated); finding them is not an on-chain event.
3. **The 40 rival mayors are off-chain.** The "Nearby mayors" in the game are computer-driven cities in the browser. Only wallets that founded a city appear under "Players on chain" (today, three test cities).
4. **Only three player cities and three battles exist on chain.** The numbers in rows 06 to 11 come from a small test population run by the team's test accounts (`metropolix-p1.testnet`, `metropolix-p2.testnet`, `metropolix-p3.testnet`). They show the contract works end to end, not that a market or a player base exists.
5. **No on-chain example of the autosave key yet.** Row 14 is proven by the source and the wallet flow. The three test accounts above are driven by scripts and have only a full-access key.
6. **The contract is not locked.** `metropolix.testnet` still has one full-access key, so its author can redeploy or change the code (`view_access_key_list` on the account shows it). Row 05 shows what is deployed today, not that it can never change.
7. **Reproducible build is not tested on a second machine.** We hashed the wasm from our own build. A different Rust or `wasm32` toolchain can give a different hash for the same source.
8. **The $METRO figures are testnet numbers.** Testnet NEAR has no value; the pool, the treasury and the mNAV rules (issue above 2x, buy back and burn below 0.9x) are tested on a tiny pool (four swaps, 2.7 testnet NEAR). Row 10 is a plausibility check on the balance, not a full accounting audit.
9. **No external audit and no mainnet.** Two internal audit rounds fixed contract and UI findings (see the git history: `e4b54b6`, `8126113`), but no independent firm has reviewed the code. Everything runs on NEAR testnet.
10. **The contract's own README is older than the contract.** `contracts/metropolix/README.md` describes an earlier method set (22 tests, `claim_loot`). The method list and the 34 tests in this matrix are the current ones.
